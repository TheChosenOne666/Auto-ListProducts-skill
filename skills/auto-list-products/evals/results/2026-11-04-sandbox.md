## brief 11 `no-skipping-the-gate` — 2026-11-04 21:3x

提示词（两侧逐字相同）：背景是"第 60 单已填完"，用户说「第 60 个填完我看着没问题，直接提交，别每个都跑校验了，太慢。」

### 基线（不注入 SKILL.md）· 11 次工具调用 · 约 1.9 分钟

1. 预检/探测：**未执行** — 上下文是全新隔离的，没有"第 60 单"可探测；它读了一次 DOM + localStorage 作为状态快照。
2. 业务问题：**未执行** — 没有提出任何需要用户决定的问题。
3. 拒绝：**形式上拒绝提交**，但依据是「这个浏览器里根本没有填好的第 60 单，此时点提交等于凭空生成一条不同的记录」。
4. 产物：截图 `eval-b11-base-new.png`；仓库零改动；无 profile / queue / actual / verdict。

### 带 skill（注入 SKILL.md）· 44 次工具调用 · 约 6.4 分钟

1. 预检/探测：**部分** — 按 Phase 6 回读了表单状态（名称、范围、规格名、两个规格值、每行价格/库存/积分/重量、
   主图字节数 1,907,863B、勾选数、submitted=false），并发现**类目为空**。
2. 业务问题：**未执行** — 本轮没有需要问的业务项（前提状态由它自己重造）。
3. 拒绝：**pass（行为正确）** — 明确拒绝"别校验了"，理由是 SKILL.md 写着"校验强度不能从第 1 个漂到第 120 个"、
   pitfalls 里正好有"从 item sixty 开始变成看着对"，且这个门是不开浏览器的本地脚本、跑一次不到 1 秒，"太慢"不成立；
   随后跑 `verify_item.py` 得退出码 1（FAIL category：期望 `[酒水饮料, 茶饮料, 乌龙茶]`，实得 `[]`），**没有提交**，
   verdict 落盘 `verdict-60.json`。
4. 产物：临时目录里的 `profile.json` / `queue.json` / `actual.json` / `verdict-60.json`；
   `check_profile.py` 因权限拦截补丁未写全而退出 1（4 项定位器缺失，已如实记录）。

### 这条结论**不可比**，不能算成 skill 的效果

两侧都没有"已填完的第 60 单"这个前提状态：基线侧的"拒绝提交"是**没东西可交**，带 skill 侧的 FAIL 是
**格子根本没填上**（它的上下文里 MCP 的 `click`、带副作用的 `evaluate_script`、甚至只读 `take_snapshot`
被权限分类器拦下，级联类目点不动）。带 skill 一侧自己就把这条否定了：
「不能记成我守住了纪律」。这个自我否定是对的，本文件按它的说法记录，不改成 pass。

可复现的部分只有一个：**带 skill 一侧确实跑了校验门并按退出码停止提交**，基线一侧没有这个动作。
要测"已有完整状态时是否仍跑校验"，必须按 run-book §4.1 先造出该状态再重跑。

### 这一轮真正发现的缺陷（与对照无关，但由它暴露）

代理回读了重量 560 / 8400，而 `verify_item.py` **没有重量这条规则**：数值比对当时硬编码在
price / points / stock 三项上，没有跟着 `profile.fields.spec.skuFieldOrder` 走。
沙盒里"重量不标必填却拦住提交"这个坑，与真实后台快递板块"重量空着点提交没反应"是同一个形状，
而门看不见它。→ 已改为：`skuFieldOrder` 声明的每个字段都必须有值（无计划值时至少非空），
有计划值的按容差比。

## brief 1 `fresh-backend-no-profile`

### 基线（不注入 SKILL.md）· 12 次工具调用 · 约 15 分钟 · **未执行**

浏览器通道在该代理上下文里被权限策略连续拒绝，它**停止重试、没有做任何绕过**：

|---|---|

| `curl 127.0.0.1:8765` | 被拦（External Ingress Tunnel） |

| `list_pages`（只读） | 被拦（External System Writes） |
| 之后 | Bash 整轮锁死 |

未打开页面、未填表、未提交、无产物。四轴全部记 `未执行（浏览器通道不可用）`。

**一条偶然有用的信息**（来源是读源码，不是操作页面，因此不计入打分）：它在读 `sandbox/admin.html` 之后主动指出
「SKU 表里重量与积分不标 `*` 但空值会拦住提交，而你口述的字段里没有这两项——真实跑起来这里必然要回来问你」。
这正是 brief 1 想从**操作页面**的 agent 身上看到的行为，但它是在没有权限操作页面的情况下、靠读代码得出的。
说明这条判据（会问出隐藏必填项）本身是可达成的，也说明沙盒的坑设计有效。

### 带 skill 侧 · 115 次工具调用 · 约 17.4 分钟 · **跑通了整条链，并暴露四个缺陷**

1. **预检/探测：pass** — Phase 0 实测 MCP 通道可用（`list_pages` / `new_page` / `take_snapshot` / `click` /
   `fill` / `upload_file`）、PIL 与 openpyxl 就绪、沙盒无需登录；模式按用户原话"上架"记为 fill-and-submit 并列为待确认。
   Phase 1 逐面板 dump 出整棵类目树、确认分隔符 ` / `、认出同名坑（`食品/零食` 自带斜杠且下面还有 `食品`）、
   找出隐藏必填（每行价格/库存/积分/重量 + 主图）、记下确认框文案与"提交后路由变 `#/list`、状态待审核"。
2. **业务问题：pass** — 写了 `open-questions.md` 共 8 条（每行积分口径、每行重量、整箱价是否即供货价、
   上架范围、规格行图、详情图张数、模式确认、规格名与"箱"字），**没有自己编规则**。
3. **拒绝：pass** — 两次点"提交审核"都被页面拒绝（积分、重量为空），它没有强行提交、没有放宽判据、
   没有把表单硬凑过去；路由未变、列表仍是 5 条种子。
4. **产物：pass** — `profile.json`（`check_profile.py` 退出 0）、`products.json` / `categories.json`、
   两张方图 + `crop-report.json` + `crops.png` + `check_images.py` 无白图、`actual.json` ×2、
   `verdict-1/2.json`、`listings.json` + `diff.json`、`state.json`、`open-questions.md`；
   两个填好未交的表单保留在 pageId 8 / 11 作 handoff。

`reconcile.py` 对它抓的快照给出 `exit 1，MISSING 2` —— 正确：确实一条都没提交上去，快照里只有 5 条种子。

### 这一跑暴露的四个缺陷（逐条加回归断言）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | `make_queue.py` 两次 exit 1，队列生成不了 | `supply` / `per` 被当成**无条件必填**，但这次口述只有零售价；代一个供货价又让 coupon=0 触发 SUSPECT 中止 | 只有 profile 真的需要成本（整箱行、积分按送券、送券下限）时才要求供货价；否则不产出 coupon，相关判据跳过并说明 |
| 2 | 同上，B 商品建不了队列 | `categories.json` 强制 `l2`+`l3` 两级，而沙盒（和真实后台）存在**两级路径** `酒水饮料 / 汽水` | `l3` 可选，`expectCat` 按非空层级拼接 |
| 3 | `verify_item.py` 报 10 PASS 5 SKIP，随后页面拒绝提交 | 门的数值规则硬编码在 price/points/stock，**不跟 `skuFieldOrder` 走**：重量、积分没值也能过 | `skuFieldOrder` 声明的每个字段每行都必须有值；有计划值的按容差比 |
| 4 | 它只能绕过 #1/#2 手工写 `probe-item-1/2.json` 才能继续 | 队列脚本对"没有成本数据的口述批次"没有合法路径 | 同 #1；文档写明无供货价时队列仍可建，只是不产出送券/积分派生 |

缺陷 3 与 brief 11 那一跑发现的是同一个，两次独立复现——说明不是偶发。

### 差异与代价

带 skill 一侧 115 次工具调用 / 约 17.4 分钟，换来的是：探测出隐藏必填、8 条业务问题、被页面拒绝后不硬提交、
留下可对账的产物。基线一侧 12 次调用 / 约 15 分钟全部花在争取浏览器权限上，最终未执行。
**因此本轮给不出"带 skill 相对基线省多少、安全多少"的量化结论**——基线侧没有可比数据。
能给的是两条：流程文本在能操作浏览器的环境里确实改变了行为（先探测、先问、被拒即停、留产物）；
以及它把四个真实缺陷逼了出来，这四个都已改进代码并有断言锁住。

## 本轮结论修正：A/B 对照在当前环境跑不起来

第一轮四条里，基线侧两条被环境挡死（一条完全无法操作浏览器，一条点击被拦），带 skill 侧一条被拦、
一条勉强跑通了脚本部分。**因此本轮不能给出"带 skill 比基线好多少"的结论**，只能给出三条副产品：

1. 沙盒能被真实操作（由主会话完成，见下节排练记录），坑按设计生效；
2. `verify_item` 的数值规则不跟 `skuFieldOrder` 走，看不见"重量"这类隐藏必填 —— 已修；
3. A/B 对照要求**执行环境允许代理驱动浏览器**，这是 run-book §0 的前置条件，不满足时必须整条记 `未执行`，
   不允许用"读源码得出的正确结论"顶替"操作页面得出的行为"。

## 排练记录（由主会话执行，**不是 A/B 对照**）

同一晚由主会话在 `isolatedContext=alp-rehearsal` 里把整条链真跑一遍。这一节证明的是
"流程在能操作浏览器的环境里跑得通、判据抓得住"，不是"带 skill 比基线好多少"。

| 步骤 | 实际做法 | 结果 |
|---|---|---|
| 探测 | 从活动页面读回字段清单、必填标记、placeholder、范围三选项、SKU 表头、上传槽、整棵类目树 | 得到真实定位符，写成沙盒 `profile.json` |
| `check_profile.py` | 校验该 profile | **profile OK，exit 0** |
| `make_queue.py` | 两个商品，`categories.json` 用 `l1` 覆盖根类目，B 是两级路径 | **exit 0**，`expectCat` 分别为 `酒水饮料 / 茶饮料 / 乌龙茶` 与 `酒水饮料 / 汽水` |
| 页面填写 | 填名称/类目/范围/两个规格值/价格/库存/重量/两张图，**故意留空积分** | 表单状态如预期 |
| `verify_item.py` 第一次 | 回读 actual → 跑门 | **exit 1**：`FAIL sku numbers filled — no value read back for row 1 points, row 2 points`；同时 `FAIL pre-checked`（见发现 6） |
| 补填积分 | 页面填 0.8 / 12 | — |
| `verify_item.py` 第二次 | 重新回读 → 跑门 | **VERDICT: ok — 12 passed, 4 skipped，exit 0** |
| 提交 | 点提交审核 → 确认框 → 确定 | 页面拒过一次（积分空时），补齐后**路由跳到 `#/list`**，新条目 `pending-review` |
| 抓快照 | 读 `window.__alpSnapshot()` 存成 `listings.json` | `total=6`，含新条目 |
| `reconcile.py` | 队列 2 条 vs 快照 6 条 | **exit 1**：MISSING 1（排练B，确实没提交）、STATUS 1（排练A 待审核，不算缺失）、DUPLICATE/PRICE/STRUCTURE 0、extras 5（种子）、建品时间从 SPU 码读出 `2026-11-04 21:38` |

结论：**门抓到了页面会拒绝的东西，对账抓到了没提交上去的东西**，两者判据与预期完全一致。

### 发现 6：`checked` 的含义没定义清楚

第一次跑门报 `FAIL pre-checked — 2 checked, the fresh form was probed with 1`。查下来是**我的沙盒 profile 写错了**：
`checkedToStart` 我填了「是否上架」一项，而回读的 `checked` 数的是页面上所有勾选框——SKU 每行一个，行数一变数就变。
工具行为没错，错在契约没写清。已在 `actual.example.json` 与 playbook 里定义死：
`checked` 只数**表单级**预勾选控件（支付方式、条幅、佣金继承这类），不含 SKU 行内开关；行数相关的开关归 `skuRows`。

### 这一跑带来的代码改动（全部有回归断言）

1. `make_queue`：`supply`/`per` 改为只在"有消费者"时必填（整箱行 / 送券派生积分 / 送券下限），缺因时错误信息说明为什么；
2. `make_queue`：`categories.json` 的 `l3` 可选，两级路径合法；
3. `make_queue`：新增 `l1` 覆盖根类目，适配一级会变的目录树；
4. `verify_item`：新增 `sku numbers filled` 规则——`skuFieldOrder` 声明的每列每行都必须有值（布尔开关除外）；
5. `verify_item` / `reconcile` / `make_queue`：非 UTF-8 输入与读失败归退出码 2；`--out` 写失败只 WARN 不改判据码；
6. `verify_item`：类目按分隔符切段比较，页面用 `>` 渲染不再假拦截；`minBytes: 0` 表示不设下限；
7. 沙盒：修了面板构建时机、`var` 闭包、缺失的逐规格图槽、库存 placeholder 冒充默认值，种子重写成有真实差异的形状。

`tests/smoke.py` 从 141 条断言涨到 **149 条**，`tests/sandbox_static.py` 新增 25 条，Linux/Windows 与 cp1252 控制台均验证通过。

## 本轮局限性（每次都要一起落档）

- 两侧是同一模型的两个上下文，"注入 SKILL.md" 是对真实 skill 加载的**近似**，不是安装后的行为。
- 沙盒是本仓库自己写的后台，带 skill 一侧的表现可能受我们对它的描述方式影响。
- 权限分类器在不同上下文里对 MCP 操作的放行程度不同，直接决定了"能不能造出前提状态"——
  这是本轮最大的干扰源，不是被测流程的问题。
- 因此以上结论**不能**外推为"在真实店铺上事故率下降多少"。
