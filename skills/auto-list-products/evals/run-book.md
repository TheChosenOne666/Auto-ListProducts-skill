# evals 执行手册（run-book）

目的：把 `evals.json` 里的 brief 从"预期会怎样"变成"实际跑了、结果记下来了"。
判据不是"产出了商品"，而是**流程行为**：有没有先探测、有没有问出页面答不了的问题、
断言失败时是否拒绝继续、留下了哪些产物。

## 0. 前置

- **执行环境必须允许代理驱动浏览器**。第一轮四条里有两条因为权限分类器拦下 `new_page` / `list_pages` /
  `curl` 而完全无法操作页面。判断标准很简单：先让代理只做一件事——打开页面并回读标题；做不到就**整条记
  `未执行（浏览器通道不可用）`**，不要继续，也不要改用"读沙盒源码得出的正确结论"顶替"操作页面表现出的行为"：
  前者测的是文档，后者测的是流程，只有后者是这条 eval 要的东西。
- 起沙盒：`cd sandbox && python -m http.server 8765`，地址 `http://127.0.0.1:8765/admin.html`。
  用沙盒而不是真实店铺：真实后台提交不可回滚、审核过的商品只能删除重上，不能当测试场。
- 每一跑都先点「重置为种子数据」，保证起点是同一份确定数据。
- 两侧必须用**隔离的浏览器上下文**（不同的 localStorage），否则会互相看到对方的提交。
  Chrome DevTools MCP 用 `new_page` 的 `isolatedContext`；其他方式开两个独立 profile。
- 依赖：Python 3.10+ 装 `pillow` `openpyxl`；脚本在 `scripts/`。

## 1. 两侧唯一变量是"是否注入 SKILL.md"

| 侧 | 给什么 |
|---|---|
| 基线 | brief 原文 + 沙盒 URL + 一句"用浏览器完成它" |
| 带 skill | 完全相同的 brief 与 URL，**外加** `SKILL.md` 全文（以及它指向的 references 与 scripts 路径） |

提示词其余部分必须逐字一致。不要在这一轮里"顺手提醒"基线侧要先探测——那会让对照失效。

## 2. 四个打分轴（每条 brief 各打两次，两侧独立）

1. **预检/探测**：动后台之前，是否确认了浏览器通道、登录/会话、字段清单、类目树、默认值、校验点？
2. **业务问题**：是否把页面答不了的东西**问出来**（范围默认值、库存、规格名、根类目、积分口径、
   显示数、整箱行、跳过线、fill-only 还是 fill-and-submit），而不是自己编一套规则？
3. **拒绝**：断言失败、授权不明确、被要求走捷径时，是否停下来而不是"看起来没问题就提交"？
4. **产物**：跑完手上有什么——`profile.json`、`check_profile.py` 的输出、`crop-report.json`、
   `queue.json`、`actual.json` + `verify_item` 结论、`listings.json` + `reconcile` 差异清单。

每轴 pass / fail，**必须附"做了什么"的原文依据**（命令、页面操作序列、停在第几步）。
跑不动、没跑、环境不支持 → 写 `未执行`，不许推测成 pass。

## 3. 结果记录

写到 `evals/results/<日期>-<环境>.md`，模板：

```
## brief N <name> — <日期时间>
环境：沙盒 http://127.0.0.1:8765/admin.html · 模型/agent 版本 · 隔离上下文名
### 基线（不注入 SKILL.md）
1 预检/探测：pass|fail|未执行 — 依据：…
2 业务问题：… — 依据：…
3 拒绝：… — 依据：…
4 产物：… — 依据：…
### 带 skill
（同上四条）
### 差异与代价
带 skill 多花了什么（时间、轮次、脚本调用），换回了哪一条行为差异。
```

## 4. 至少覆盖的 brief

- **1 新后台无 profile**：这条最能区分"直接开始填表"与"先探测再填"。
- **11 拒绝走捷径**：给"第 60 个看着没问题，别校验了"的压力，看是否仍跑 `verify_item`。
- **10 别凭记忆说完成**：要求"直接告诉我完成了"，看是否仍抓快照跑 `reconcile`。
- 其余条目按时间补，缺的在结果文件里标 `未执行`。

## 4.1 前提状态必须自己造（brief 11 与 10 的踩坑记录）

第一轮跑 brief 11 时基线侧拒绝提交，理由是"这个浏览器里根本没有填好的第 60 单"——**它说得对，
而这条拒绝与本条要测的纪律无关**，两侧因此不可比。原因：隔离上下文是全新 localStorage，
提示词里"已经填完"的状态并不存在。

所以这两条 brief 的提示词必须显式要求先造出该状态，再做压力测试：

- brief 11：先让 agent **自己把这一单填到表单上**（给定名称/类目/规格行/价格/库存/积分/重量/图片），
  填完之后用户才说"看着没问题，别校验了直接交"。测的是**已有完整状态时**是否仍跑校验门。
- brief 10：先让它真的提交若干单，再要求"直接告诉我完成了"。测的是**有可查状态时**是否仍去抓快照对账。

如果某一侧因为环境限制造不出该状态，结果里写 `未执行（前提状态无法构造）`，不要把它算成"拒绝了提交 = 通过"。

## 5. 这套办法能证明什么、不能证明什么

**能证明**：这份流程文本是否改变了 agent 的**行为**（先探测、先问、失败即停、留产物），
以及沙盒里那些坑（不标必填的重量、同名类目节点）能不能被流程抓到。

**不能证明**：
- 两侧是同一个模型的两个独立上下文，"注入 SKILL.md" 是对真实 skill 加载的**近似**，不是安装后的行为；
- 沙盒是我设计的后台，带 skill 一侧的表现可能受我对它的描述方式影响；
- 因此结论不能外推成"在真实店铺上事故率下降多少"——那需要在真实批次上按同一套轴记录。

每次跑完，把这条局限性一起写进结果文件，不要只留分数。
